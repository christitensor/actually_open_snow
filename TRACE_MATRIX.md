# OpenSnow Feature Trace Matrix

This matrix inventories the real, shipped feature set of OpenSnow (as of Aug 2026, sourced primarily from OpenSnow's own [Support Center feature guides](https://support.opensnow.com/feature-guides), App Store listing, and public reporting) and tracks the build status of an independent, open-data reimplementation in this repo.

This project does **not** replicate OpenSnow's subscription tiering — every feature below is being built as a single, ungated tier. The `Access Tier` column from the original product has been dropped; a `Data Source Plan` column replaces it, mapping each feature to the free/open data source we'll use instead of OpenSnow's proprietary PEAKS/StormNet models.

See `ARCHITECTURE.md` for the technical design these data sources plug into.

**Build status (Aug 2026):** the P0/P1 work and a first pass of P2 breadth features are implemented and verified against live APIs — see "Implementation notes" at the end of this file for real bugs found and fixed along the way (they weren't hypothetical caveats; every one of them was hit live), including a genuine Open-Meteo rate-limit encountered from this session's own testing volume.

## Phase 1 regional scope: Northern Utah & Southeast Idaho

To maximize data quality while the app is being built, all P0/P1 work targets **Northern Utah and Southeast Idaho** only — everything in this matrix is designed to generalize nationally later, but the seed data (RES-01/RES-02) and any manual curation (webcams, trail maps) starts scoped to this region. Reasons this region specifically maximizes free-data quality:

- **Single/dual NWS forecast office coverage** — Salt Lake City (WFO SLC) covers northern Utah; Pocatello (WFO PIH) covers southeast Idaho. Fewer offices to reconcile than a nationwide launch.
- **Dense SNOTEL network** — the Intermountain West (Utah/Idaho) has one of the densest NRCS SNOTEL station networks in the country, so snowpack ground-truth data (DATA-01, SNOW-03 corroboration) is unusually good here.
- **Utah Avalanche Center** covers the Salt Lake, Ogden, Logan, and Provo zones (northern Utah); backcountry near the Utah/Idaho border and the Tetons is covered by neighboring centers — exact zone-to-resort mapping needs confirming per location during BC-01 build-out.
- **UDOT** publishes a free (developer-key-required, no cost) camera API covering the Cottonwood Canyons and other Wasatch corridors — a strong seed for MAP-16. **Idaho 511 / ITD** is the parallel source for southeast Idaho corridors.

Initial resort/location seed list (editable, not exhaustive) for RES-01:

- **Northern Utah**: Alta, Snowbird, Brighton, Solitude, Park City, Deer Valley, Snowbasin, Powder Mountain, Nordic Valley, Beaver Mountain, Cherry Peak, Sundance
- **Southeast Idaho**: Pebble Creek, Kelly Canyon, Pomerelle Mountain Resort, Grand Targhee (borderline — technically Wyoming, but the primary access/gateway community is Driggs, ID, so worth including)

## Implementation notes from the first build pass (Aug 2026)

The P0 slice and backcountry-first P1 work (FC-01/02/03/04/07/10/11, MAP-01/11/13/17, SEV-01, SNOW-01/03, BC-01/02, PERS-01, RES-01/02) were built and verified against **live** external APIs, not just planned. Several of the matrix's "unverified, confirm during build" caveats turned out to be real bugs, not hypothetical risk — worth recording so they aren't rediscovered:

- **avalanche.org**: the forecast zone id is the GeoJSON `Feature.id` (top-level), not `properties.id` — the latter doesn't exist on the feature at all. `properties.center` holds the full center name; there is no `properties.center_name`.
- **NRCS SNOTEL (AWDB REST API)**: station filtering requires `stationTriplets=*:UT:SNTL,*:ID:SNTL` (wildcard syntax). The originally-planned `networkCds`/`stateCds` query params are silently ignored — the request still returns HTTP 200 with all ~4,390 US stations nationwide, which reads as "it worked" until you check the count. The `/data` endpoint requires `beginDate`/`endDate` (relative values like `-3`/`0` work); there is no `durationCount`/`periodRef=END` shortcut.
- **Overpass API** (OSM piste data): returns HTTP 406 for any request that doesn't send an explicit `User-Agent` and `Accept` header — confirmed by reproducing with Node's native `fetch` (406) vs. `curl` (200) for an otherwise-identical request. Once headers are added it works, though the public instance is occasionally slow (seconds, sometimes a 504) — handled as a soft failure so a slow piste layer doesn't break the rest of the page.
- **NWS AFD text products** (`api.weather.gov/products`) and the **NWS gridpoint `snowLevel` field** both worked exactly as documented on the first live call — no surprises there.

## Implementation notes from the fourth build pass — per-day snow line, hourly forecast, wind, elevation adjuster, resort webcams, UI polish (Aug 2026)

Added FC-10's per-day snow line, surfaced the already-fetched hourly forecast (FC-02), wind gust/direction (new FC-12), the elevation-adjuster slider (new FC-10-adj), resort-specific webcams on each location page (MAP-16), and a small UI polish pass. Two real, non-obvious bugs were caught by live-testing the new per-day snow line rather than assumed correct:

- **`freezing_level_height`'s unit silently changes based on the other unit params in the same request.** `getForecast()`'s hourly freezing-level conversion (`value * 3.28084`, meters→feet) predates this pass and was already live — but it was wrong the whole time, just masked: the "current snow level" stat tile and `elevationVsSnowLine()` both prefer NWS's `snowLevelFt` when available, so the bad value rarely surfaced directly. Adding a per-day fallback to `freezingLevelFt` for days beyond NWS's ~7-day window exposed it immediately as a physically-impossible **51,990 ft** snow line. Root cause, confirmed by diffing the raw JSON from the exact URL `getForecast()` builds: with `temperature_unit=fahrenheit` set (as this app's request always does), Open-Meteo's `hourly_units.freezing_level_height` comes back `"ft"`, not `"m"` — the imperial-unit request implicitly switches the height unit too. The `* 3.28084` was re-converting an already-imperial value, inflating it ~3.3x. Fixed by removing the conversion entirely for this field (verified: 51,990 ft → a plausible 15,846 ft for the same hour). `getElevation()`'s meters→feet conversion is unaffected — it hits a separate endpoint (`/v1/elevation`) that has no unit params and always returns meters.
- **A naively-parsed "2pm local" target timestamp silently meant "2pm UTC" instead**, because `day.date + "T14:00"` has no timezone attached and `new Date()` interprets it using the server process's own timezone (UTC in this environment) rather than the location's actual offset. This stayed invisible when matching against Open-Meteo's own hourly array (also offset-less local-time strings — both sides get the same misinterpretation, which cancels out), but broke matching against NWS's `validTime`, which carries a real UTC offset: the "afternoon" snow line was actually being matched against NWS's ~8am-local reading, off by the full UTC offset (~6-7h for this app's Mountain-time coverage). Fixed by threading Open-Meteo's own `utc_offset_seconds` (now exposed as `ForecastResponse.utcOffsetSeconds`) through to `computeDailySnowLines()`, which uses it to build a genuine UTC instant for the NWS-side comparison only (the Open-Meteo-side comparison correctly stays on the naive/self-consistent target). **Takeaway shared with both bugs above: a plausible-looking derived number (a snow line a few thousand feet off, in particular) is exactly the kind of error that passes casual review — both were only caught by actually running the new code against live data and sanity-checking the output against physical reality, not by reading the code.**
- **Open-Meteo's `elevation` override param is real and does more than a fixed temperature lapse rate** — live-verified with three requests at the same lat/lon, varying only `elevation`: both `temperature_2m_max/min` *and* `precipitation_sum` changed with elevation (not just temperature), confirming it's a genuine model-downscaling parameter rather than a client-side lapse-rate trick worth reimplementing. Backs the new elevation-adjuster slider via a lean, daily-only, 7-day `getElevationAdjustedDaily()` (deliberately not the full `getForecast()` shape, since this refetches on every slider move).
- **UI polish was verified visually, not just by code review** — took real Playwright screenshots (iPhone viewport, both themes) of the location dashboard and home page rather than assuming the redesign "looked fine." Caught two concrete issues this way: the elevation slider was the one control still using unstyled browser-default chrome next to an otherwise fully custom design system (fixed with explicit `::-webkit-slider-thumb`/`::-moz-range-thumb` styling), and the home page's map (`h-[55vh]`) pushed the user's own pinned Snowbasin/Beaver Mountain cards below the fold on a phone screen — directly undercutting the "put those at the top" request from an earlier pass (shrunk to `h-[38vh]` on mobile, unchanged on larger screens). Also confirmed via a non-fullPage viewport screenshot that an apparent bottom-nav/content overlap seen in `fullPage` captures was a Playwright screenshot-stitching artifact with `position: fixed` elements, not a real rendering bug — worth knowing before "fixing" something that was never broken.

## Implementation notes from the sixth build pass — turning link-out webcams into real live cameras (MAP-16)

Went back into MAP-16 specifically to convert as many page-link-only entries as possible into real live content, per a direct ask ("get these webcams to actually show up and not just link out"). Went from 2 live cameras (Snowbird only) to 17 across 3 resorts:

- **Snowbasin (7 cams) required a two-hop resolution, not a one-line fix.** Its webcam page uses the same HD Relay vendor as Snowbird, but embeds the player via a small client-side widget (`HDRelay.create({target, id})`) instead of a plain `<img src>`, so the id sitting in static HTML isn't directly usable as a snapshot URL the way Snowbird's was. The real snapshot path is also different from Snowbird's: `/camera/{camera.id}/get_image`, not `/snapshot` — found by fetching and reading the newer player's own JS bundle (`cdn.hdrelay.com/js/player-2021/index.js`) rather than guessing at REST conventions. All 7 verified live by decoding the response as a current JPEG with a matching EXIF capture timestamp.
- **Solitude (10 cams) doesn't publish still images at all — it embeds YouTube livestreams per camera.** Confirmed these are genuine current live feeds (not old recorded video) via each video's public, keyless oEmbed title (`youtube.com/oembed?url=...&format=json`), which returned clear camera-style names ("Moonbeam Lift Line", "Solitude Snow Stake", "Honeycomb Canyon") rather than generic video titles. Added a new `Webcam.videoEmbedUrl` field alongside `imageUrl` (mutually exclusive) and a matching `<iframe>` branch in `WebcamGrid`, which deliberately never reloads/cache-busts video embeds the way it does for still images — forcing an iframe reload would interrupt playback for a feed that's already continuously live.
- **Confirmed, don't assume, why the JS-heavy resorts (Alta, Powder Mountain) couldn't be resolved the same way**: their pages use a different third-party vendor ("PrismCam"/`js.prismcam.com`) whose camera list is populated entirely client-side by custom elements (`<mountain-cams>`) with zero server-rendered ids or config in the HTML — nothing to scrape at all, unlike HD Relay's widget which at least left an id in a `data-` attribute. The next step for these would be executing the page's own JS, so this was tested directly with a real headless Chromium (Playwright) rather than assumed impossible — and found that **this deployment's sandbox blocks all outbound browser network access**, even to a trivial test URL, while the app's own server-side `fetch()`/curl calls succeed through the identical proxy. That's an environment-level constraint on *browser* traffic specifically, not a per-site block or a proxy misconfiguration worth chasing further here.
- **Two stale seed URLs were caught and fixed as a side effect of this investigation**: Snowbasin's original `pageUrl` (`/mountain-report/mountain-cams/`) 404s — the resort restructured its site since the URL was first seeded; the real page is `/the-mountain/web-cams/`, found via the resort's own homepage nav. Park City's original `.aspx` URL returns HTTP 200 but is a dead legacy page rendering an internal system error ("The system cannot process your request") — replaced with the resort's current `/todays-conditions` page. Both `pageUrl` fixes are a direct, if incidental, correctness improvement on top of the live-camera work, caught only because this pass actually fetched and read every resort page rather than trusting the original seed data.
